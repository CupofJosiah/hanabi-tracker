# Architecture

The app exists to produce one artefact: a hanab.live export JSON of a game
played with physical cards. Everything is arranged around that.

## The one idea

**A game is `deck` + `actions`. Everything else is replayed from them.**

That is also exactly hanab.live's export format, so exporting is a formatting
step rather than a translation, and there is no second model to keep in sync.

```
GameRecord { players, ourPlayerIndex, variantName, deck[], actions[], ... }
        │
        │  replay()
        ▼
GameState  { hands, cards, playStacks, discards, clueTokens, strikes,
             currentPlayerIndex, cardsRemaining, finished, log }
```

Recording a turn appends to `actions` (and to `deck`, if a card was drawn) and
the whole game is replayed. Games run to a couple of hundred actions, so this
costs microseconds and buys three things for free:

- **Undo** — drop the last action, truncate the deck back to what had been drawn.
- **History scrubbing** — `replay(record, n)` is the board after `n` actions.
- **Crash safety** — the saved record *is* the game; there is no derived state
  that can be saved in a torn condition.

## Orders, slots and deal order

A card is identified by its **order**: its index in `deck`, which is the order it
was dealt or drawn. Plays and discards target an order. Two conventions come
from hanab.live and must be matched exactly or the export replays wrong:

- The deal is **per seat, not round-robin**: seat 0's whole hand, then seat 1's,
  then the draw pile.
- Every draw becomes **slot 1**, so within a seat's opening block the *highest*
  order is slot 1 and the lowest is the oldest card.

`initialDeckIndex()` in `recording.ts` is that mapping, and `engine.ts` deals the
same way. `recording.test.ts` pins both down; `engine.test.ts` replays a real
four-player game and `hanabLive.test.ts` re-exports it byte for byte.

## The hidden hand

The recorder cannot see their own cards, so those deck entries stay
`{suitIndex: -1, rank: -1}` until something reveals them:

- **Playing or discarding one** turns it face up, so the app asks for its
  identity at that moment — offering only identities that are still possible.
- **After the game**, the review screen lists whatever is left.

This has one consequence worth knowing about. Clue-touch is normally *derived*:
given the deck and the variant's rules, the engine knows which cards a clue
touched. It cannot do that for a clue aimed at the hidden hand, so there the
recorder taps the touched slots and the answer is stored in
`record.touchedByAction[actionIndex]`. That field is **not** exported — hanab.live
recomputes touches from the deck — but it is what powers the "what could this
be?" display, and it constrains the post-game fill-in.

`deduce.ts` turns that into candidate lists: an identity is possible for a hidden
card when copies of it remain unseen *and* it satisfies every positive and
negative clue on that card. `autoResolve()` repeatedly settles cards down to one
candidate, which after a full game usually cracks most of a hand at once.

## Variants

`variantData.ts` is generated by `tools/gen-variants.mjs` from hanab.live's
upstream `variants.json` / `suits.json` / `colors.json`, and committed so the app
never touches the network. It carries the 491 variants whose suits map 1:1 onto
clue colours — the subset both this app's clue logic and scala-bot model
correctly. Ambiguous and dual-colour families (Tomato clued by Red, Yam clued by
Red *or* Yellow) are deliberately excluded rather than silently mis-exported.

`variants.ts` builds the runtime model: deck composition, which colour clues
exist, and `cardTouched()`. Those rules mirror scala-bot's `Variant.idTouched`,
because a clue recorded here has to mean the same thing when the analyser replays
it. A colour clue's exported `value` is an index into the variant's *colourable*
suits, skipping Rainbow, White, Prism and friends.

## Layout

```
src/
  lib/hanabi/          no DOM, no storage — the whole game model
    types.ts           GameRecord, GameAction, Identity, hand sizes
    variantData.ts     generated suit and variant tables
    variants.ts        runtime variant model and clue-touch rules
    engine.ts          replay() -> GameState, plus legality helpers
    deduce.ts          what a hidden card could be
    recording.ts       pure record -> record turn recording, and undo
    hanabLive.ts       export, import, and pre-export validation
  lib/state/
    storage.ts         localStorage, one key per game, memory fallback
    app.svelte.ts      game list, current screen, toasts
  lib/ui/              CardFace, IdentityPicker, Sheet, share helpers
  lib/game/            board pieces: hands, stacks, discards, clue sheet, log
  lib/views/           Home, Setup, Game, Review
```

The dependency arrows only point one way: `views` → `game`/`ui` → `hanabi`.
Nothing under `lib/hanabi` imports Svelte or touches the DOM, which is why most
of the test suite is plain function calls.

## Storage

One `localStorage` key per game (`hanabi-tracker/v1/game/<id>`) plus a settings
key. Per-game keys mean recording a turn rewrites a few kilobytes instead of the
whole history, and a failure can only affect the game in progress. A corrupt
entry is skipped on load rather than taking the library down with it, and if
`localStorage` is unavailable at all, an in-memory shim keeps the session
working (with a warning when a save fails).

There is no server and no account. `exportBackup()` / `parseBackup()` cover
moving a history between devices.

## Offline

`vite.config.ts` emits a small service worker at build time listing the hashed
bundle files, cache-first with a per-build cache name, and falls back to the
cached shell for navigations. Assets are referenced relatively (`base: "./"`), so
one build works at a GitHub Pages project path, at a custom domain, or from disk.
